## Evidence method and provenance

This comparison used current repository documents and the earlier durable evidence, then directly checked the official external sources listed below for the specific mechanism propositions used here. No prototype, attack, user study, provider call, production run, benchmark or security measurement was performed. **R** = repository authority or observed repository state; **E** = attributable external documented fact/guidance; **I** = logical inference from named premises; **A** = bounded analytical assumption, not a requirement; **U** = unresolved question. A documented property is not proof that a future implementation possesses it. External guidance does not create Product, Security or Architecture authority for this repository.

The common analytical model assumes, **only for comparison**, that an already-authoritative stable Identity/current-email pair and an Identity-owned acceptance boundary could exist. The present current-email source has no lawful production population issuer, so this model is not a claim of production readiness. Each hypothetical proof is generated securely, bound to that pair, accepted only after valid presentation, and subject to the same source-backed currentness, one-use effect and fail-closed duties. No numeric code space, token size, duration, attempt budget, rate, secret-storage or key-management implementation is assumed. Unequal safeguards would make the comparison circular rather than evidential.

## Candidate-by-candidate comparative assessment

**A — short user-entered one-time code.** **E1** supports manual entry as a confirmation representation; **R1–R3** demand the same exact Identity/current-email binding and acceptance gate as for B. **I:** Human entry avoids making a proof-bearing URL inherent to the presentation category, but the code still passes through a message, user input and possible support/telemetry surfaces. “Short” constrains the likely proof space; without an accepted attempt/validity/abuse envelope, random guessing risk cannot be quantified. Manual entry may support a different-device workflow and may impose transcription or accessibility costs; **U:** no repository data establishes their comparative magnitude. Mailbox compromise, forwarding or phishing can expose A. No code length, alphabet, proof space, limit or design is selected.

**B — high-entropy verification link/token.** **E1** supports a secure-link representation; **E4** documents conditional Referer exposure. **I:** A larger unpredictable token can lower blind online guessing but not theft, forwarding, phishing, mailbox compromise or URL disclosure. Query/path placement could expose a bearer secret through browser/history/server/proxy/referrer/log/copy surfaces; RFC 9110 does **not** say fragments are sent in Referer. Link opening, scanning or prefetch is not accepted verification under **R2/R3**, so a future interaction must establish deliberate valid presentation without inventing a Contract here. A link may reduce manual transcription but may complicate cross-device use. **U:** actual browser flow, token placement, scanner behavior, accessibility and residual leakage are unmeasured. No token size, placement, click behavior or URL policy is selected.

**Comparative inference:** A's guessing burden and B's bearer/URL burden are real *different questions*, not a ranking. A hypothetical A with weak online controls cannot fairly be compared with a hypothetical B that has strong leak controls, or vice versa. Product's mobile/accessibility and Security's privacy/abuse rules apply to both; they provide no accepted weight or observed result that converts these differences into a repository-specific winner.

## One-use and authoritative-state conclusion

**R2/R3:** Accepted verification must bind to a current authoritative email, produce one bounded accepted effect, withstand duplicate/replay/reissue and not restore verification after supersession. **I:** A signed or derived proof can attest integrity and expiry but, by itself, cannot establish whether it was consumed, immediately invalidated, superseded by reissue, or concurrently accepted elsewhere. Both A and B therefore need authoritative **server-side state or evidence at the semantic level** for consumption/reissue/currentness and durable accepted outcome, even if their external proof representations differ. This is not a decision to store a per-proof row; an authoritative epoch, record or equivalent may be considered later, but no design is selected here. An existing current-email binding row supplies currentness infrastructure only, not accepted verification evidence. Its missing lawful population issuer remains a common production blocker, not a comparative advantage.
