# Java Standards

## 1. Purpose

This document refines Java-specific implementation conventions for the repository under the Java 21 LTS baseline established by ARCHITECTURE.md. It is a lower-level implementation standard subordinate to .ai/core/ and the Approved SPRING.md standard.

This document governs Java language use, type safety, object design, standard-library use, runtime compatibility, and Java-specific implementation quality. It MUST NOT redefine Product behavior, Architecture, security, testing, Spring behavior, API Contracts, persistence, database design, or event Contracts.

## 2. Scope

This standard applies to repository-owned Java production code, test code, build-time Java configuration, generated Java where repository rules apply, and Java-facing integration boundaries.

Spring-specific implementation remains governed by .ai/backend/SPRING.md. API, database, PostgreSQL, and event details remain the responsibility of their applicable Approved sources when established.

## 3. Repository Authority

Java implementation decisions MUST follow the Decision Hierarchy in AGENTS.md.

- GLOSSARY.md governs canonical terminology.
- PRODUCT.md governs Product behavior and business semantics.
- ARCHITECTURE.md governs the Java baseline, Modules, dependency direction, Domain ownership, and trust boundaries.
- SECURITY-STANDARDS.md governs mandatory security Requirements and Security Exceptions.
- TESTING-STANDARDS.md governs verification and Testing Exceptions.
- CODING-STANDARDS.md governs repository-wide implementation quality and Coding Exceptions.
- ENGINEERING-PRINCIPLES.md provides decision heuristics within governing constraints.
- DOCUMENTATION-STANDARDS.md governs documentation quality and Documentation Exceptions.
- DECISIONS.md governs durable Decision Records and ADRs.
- SPRING.md governs Spring-specific implementation detail.

This document MAY refine Java-specific implementation consequences but MUST NOT silently override a higher-authority Requirement, Accepted Decision Record, or Approved lower-level rule within its owned scope.

## 4. Normative Language

- MUST and MUST NOT express mandatory requirements or prohibitions.
- SHOULD and SHOULD NOT express expected practices whose departure requires reviewable justification.
- MAY expresses a permitted option.

These meanings apply in prose, lists, tables, and review criteria.

## 5. Java Baseline

Java 21 LTS is mandatory because ARCHITECTURE.md owns the backend runtime baseline. This document MUST NOT independently change the Java major version.

A Java major-version or runtime-baseline change requires Architecture governance, compatibility evidence, an ADR, and synchronized governing updates. This document does not select a JDK distribution or exact JDK patch release.

## 6. Source, Target, and Runtime Compatibility

Production Java source, generated bytecode, dependencies, and deployment runtime MUST remain compatible with Java 21. Build configuration MUST align source language level, target bytecode level, toolchain, tests, and production runtime.

Contributors MUST NOT silently compile against newer Java language features, standard-library APIs, or runtime behavior than the approved deployment runtime supports. Compatibility MUST be verified in the approved Pipeline and deployment environment.

This standard remains build-tool neutral until repository governance selects a build tool.

## 7. Runtime and Patch Updates

JDK security and patch updates MUST remain on a supported line, be security-reviewed, tested, and compatible with the approved build and deployment Environments.

Runtime updates MUST verify compilation, Unit Tests, Integration Tests, framework compatibility, dependency compatibility, startup, observability, performance-sensitive behavior, and deployment behavior as applicable. Patch adoption MUST NOT silently change the Java major baseline or introduce an ungoverned distribution dependency.

## 8. Language-Feature Policy

Stable Java 21 language features MAY be used when they materially improve correctness, readability, or maintainability and remain compatible with Architecture and tooling.

Records, sealed types, pattern matching, switch expressions, text blocks, local variable type inference, and enums MUST be selected for their semantics rather than novelty. Ordinary Java SHOULD be preferred when a newer construct would obscure ownership, control flow, Domain meaning, security behavior, or debugging.

## 9. Records

Records MAY represent immutable transport values, application values, simple Value Objects where all required semantics fit the record model, and Messages where the applicable Contract permits them.

Records MUST NOT automatically replace Entities, Aggregates, objects with a mutable lifecycle, or persistence representations whose identity, proxy, construction, or mutation semantics differ. A record declaration does not by itself establish valid Domain state.

Record components MUST be validated at the applicable boundary and MUST comply with Sensitive Data minimization, equality, serialization, and logging rules.

## 10. Sealed Types

Sealed classes and interfaces MAY model a genuinely closed set of permitted variants when closure is owned and stable.

Sealed types MUST NOT artificially close a Port, Adapter extension point, provider integration, or other boundary that Architecture expects to remain extensible. The permitted hierarchy MUST remain cohesive, reviewable, and tested for exhaustive behavior.

## 11. Pattern Matching and Switch

Pattern matching and switch expressions SHOULD provide concise, exhaustive, readable handling of stable alternatives. Governed closed hierarchies SHOULD avoid a default branch where compiler-checked exhaustiveness provides stronger safety and future variants must trigger review.

Complex nested patterns, guards, or switches MUST NOT conceal Domain policy, Authorization, side effects, or lifecycle transitions. Behavior that belongs to a Domain concept or polymorphic boundary SHOULD remain with its proper owner.

## 12. Text Blocks

Text blocks MAY improve readability for multiline test data, templates, or project-owned static content. Their indentation, line endings, escaping, formatting or template processing, and trailing whitespace MUST be understood and tested when externally observable.

Text blocks MUST NOT embed Secrets, production credentials, uncontrolled SQL, or an undocumented external Contract. Large schemas, templates, and Contracts SHOULD remain in governed resource files where ownership and tooling require it.

## 13. Local Variable Type Inference

Local variable type inference with var MAY be used only when the inferred type is immediately obvious from nearby code and improves readability.

var SHOULD NOT be used where it hides Domain meaning, numeric precision, a generic type, an API or Adapter boundary, ownership, mutability, or a security-sensitive type. It MUST NOT be used for fields, method parameters, constructor parameters, or return types.

## 14. Null Handling

Required inputs MUST be validated at trusted boundaries and invalid absence MUST fail clearly. Methods MUST NOT return null collections; an empty collection SHOULD be returned where emptiness is the correct semantic result.

Optionality MUST be explicit in the method Contract, type, validation, or documentation as appropriate. null MUST NOT serve as an undocumented lifecycle state, authorization signal, success indicator, or substitute for a governed Domain state.

Null annotations MAY be adopted only through repository dependency and tooling governance and MUST NOT create false confidence without enforcement.

## 15. Optional

Optional SHOULD primarily represent an expected absent return value. It MUST be used deliberately and MUST NOT be required for every potentially absent concept.

Optional SHOULD generally be avoided as an Entity field, DTO field, method parameter, or collection element unless a specific Contract and serialization model justify it. Code MUST NOT call get() without already establishing presence.

Optional MUST NOT disguise invalid input, validation failure, infrastructure failure, or an unknown lifecycle outcome. Nested Optional values and Optional collections SHOULD be avoided.

## 16. Immutability

Objects and fields SHOULD be immutable and final where doing so preserves clear ownership and correct behavior. Domain correctness and an explicitly owned lifecycle take precedence over artificial immutability.

Mutable internal collections MUST NOT be exposed. Defensive copies, unmodifiable views, or immutable copies MUST be used where an ownership boundary requires them, with the choice reflecting whether a snapshot or live view is intended.

## 17. Collections

Public APIs SHOULD depend on the least-specific collection interface that expresses required semantics. List, Set, and Map MUST be chosen according to ordering, duplicate, lookup, and key semantics rather than convenience.

Collection ordering MUST be intentional when externally observable. Duplicate behavior and null acceptance MUST be explicit. Operations over untrusted or externally supplied collections MUST enforce applicable size and resource bounds.

Returned collections MUST NOT expose mutable internal state. Empty collections SHOULD be preferred over null where absence and emptiness are semantically equivalent.

## 18. Streams

Stream APIs MAY be used when they make transformation, filtering, grouping, or aggregation clearer than an imperative alternative.

Deeply nested pipelines, hidden side effects, mutation during traversal, exception-heavy operations, and pipelines that are difficult to inspect or debug SHOULD be replaced with focused methods or explicit control flow. Streams MUST NOT obscure a stateful workflow, Database Transaction boundary, retry, Authorization decision, or Domain transition.

## 19. Parallel Streams

Casual use of parallelStream() in server code is prohibited. Adoption requires measured evidence for the workload, thread-pool behavior, request isolation, data size, blocking behavior, operational limits, and material performance benefit.

Parallel streams MUST NOT perform provider calls, blocking database work, or security-context-dependent behavior without an explicitly reviewed concurrency design. Spring asynchronous work and Background Jobs remain governed by SPRING.md.

## 20. Equality and Hashing

equals() and hashCode() MUST be consistent, symmetric, transitive, null-safe, and based on stable semantics appropriate to the type.

Value Objects SHOULD use all value-defining attributes. Entity equality MUST reflect stable identity semantics and MUST NOT be derived blindly from every mutable field. Mutable fields used in hashing MUST NOT make collection membership unreliable.

Persistence-specific equality behavior remains governed by an applicable Approved persistence standard and the selected technology when established.

## 21. String Representation

toString() MUST be deliberate and safe. It MUST NOT expose Secrets, credentials, Access Tokens, Refresh Tokens, Session secrets, raw CVV, cryptographic material, unnecessary PII, or other Sensitive Data.

Generated or record-provided string representations MUST be reviewed rather than assumed safe. Types containing sensitive values SHOULD omit, redact, or replace them with non-sensitive diagnostic identifiers.

## 22. Money

Java code representing Money MUST preserve the canonical model of an amount and explicit ISO 4217 Currency. Authoritative monetary calculations MUST use BigDecimal or an approved Money abstraction and MUST NEVER use float or double.

Money operations MUST prevent accidental arithmetic across different Currency values. Rounding, scale, allocation, tax, Discount, Price, Payment, Refund, and Settlement behavior MUST follow the owning Product Requirement or Domain Specification.

Java code MUST NOT invent a rounding or scale policy when Product governance has not established one.

## 23. BigDecimal

Decimal constants MUST be constructed from exact strings, integer values, valueOf() where its semantics are suitable, or another exact approved source. new BigDecimal(double) is prohibited for authoritative decimal values.

Code MUST distinguish BigDecimal.equals(), which is scale-sensitive, from compareTo(), which compares numeric value. Money equality and ordering MUST use the semantics of the approved Money abstraction or owning Domain rule.

Scale and RoundingMode MUST be applied deliberately at a governed calculation boundary. A local method MUST NOT introduce an arbitrary rounding mode for Price, tax, Payment, Refund, or other financial calculations.

## 24. Time

New code MUST use java.time APIs. Instant SHOULD represent machine timestamps; LocalDate SHOULD represent a calendar date without time or offset; LocalDateTime, OffsetDateTime, and ZonedDateTime MUST be chosen according to the actual Contract; Duration SHOULD represent elapsed time.

Legacy Date and Calendar MUST NOT be introduced in new code except at a justified integration boundary, where they SHOULD be translated immediately into an appropriate java.time type.

Persisted and system timestamps MUST follow the UTC guidance in ARCHITECTURE.md and SPRING.md. This document does not create Customer locale or Time Zone policy.

## 25. Clock

When current time affects business eligibility, expiration, lifecycle, retries, reconciliation, or another testable behavior, code SHOULD use an injected java.time.Clock or an equivalent project-owned Port.

Scattered calls to Instant.now(), LocalDate.now(), or the system clock MUST NOT make Domain behavior nondeterministic or difficult to test. Framework or infrastructure code MAY read the system clock directly where the behavior is purely technical and explicitly bounded.

## 26. Identifiers

Strongly meaningful identifier types SHOULD be used when they materially prevent cross-Entity, cross-Module, or cross-Domain mistakes. Wrapper types MUST justify their conversion, serialization, equality, and maintenance cost.

Not every identifier requires a wrapper. Identifier values MUST remain immutable, validated, and compatible with the owning Contract.

An identifier supplied by a client is a lookup candidate only. Java code MUST NOT infer Resource ownership or Authorization solely from its presence or value.

## 27. Enums

Enums SHOULD represent genuinely closed, stable code-level sets. Enum names MUST use singular PascalCase, and constants MUST use the repository's Java naming conventions.

Rapidly changing Product configuration, provider values, or data-owned classifications MUST NOT be encoded as enums merely for convenience. Lifecycle enums MUST align exactly with the owning Aggregate lifecycle and governing Specification.

Unknown external values MUST be handled according to the applicable Contract and compatibility policy rather than silently mapped to an unrelated default.

## 28. Exception Categories

Java code MUST keep domain or application failures, validation failures, infrastructure or provider failures, and programming defects distinguishable where recovery, translation, retry, or observability differs.

Exceptions MUST NOT be swallowed, used as normal collection control flow, or exposed directly to external clients. Broad catch clauses are prohibited except at an intentional outer boundary responsible for safe translation, diagnostics, or termination.

SPRING.md owns HTTP exception translation and RFC 9457 Problem Details behavior.

## 29. Checked and Unchecked Exceptions

Checked and unchecked exceptions MUST be selected intentionally based on recoverability, caller obligations, boundary semantics, and the libraries involved. This standard does not impose an ideological blanket rule.

Provider or library checked exceptions SHOULD be translated at the owning Adapter boundary into project-owned failures rather than leaking through Application Services or the Domain. Translation MUST preserve distinctions needed for retry, reconciliation, or fail-safe behavior.

## 30. Exception Causes and Messages

Useful causes MUST be preserved when translating an exception unless doing so would cross an unsafe external boundary. Exception messages MUST provide safe technical context without Secrets, credentials, tokens, raw provider payloads, or unnecessary Sensitive Data.

The same failure SHOULD NOT be logged and rethrown at every stack layer. Logging SHOULD occur at the boundary that owns response, recovery, or operational action, with Correlation ID and safe context where applicable.

## 31. Generics

Generics MUST improve type safety and express meaningful relationships. Raw types are prohibited.

Unchecked casts require narrow, reviewable justification and focused tests. Warning suppression MUST be scoped to the smallest construct and explain why type safety is established.

Deep generic hierarchies and wildcard-heavy APIs SHOULD be avoided when they obscure Domain meaning, ownership, or usage.

## 32. Static State

Mutable global or static state is prohibited. Static state MUST NOT hold request context, Principal, Authorization data, mutable caches, provider clients, clocks that affect business behavior, or test coordination.

Static constants and pure stateless utility functions are acceptable. Static initialization MUST remain deterministic, safe, and free of hidden external effects.

## 33. Utility Classes

Utility classes MUST be focused, cohesive, and stateless. They MUST NOT become generic dumping grounds named Utils, CommonUtils, Helper, or similar when behavior belongs to a Domain concept, Value Object, Domain Service, Application Service, or Adapter.

A utility method MUST have explicit inputs and outputs and MUST NOT hide I/O, configuration lookup, time, randomness, or security context.

## 34. Naming

- Classes, interfaces, records, enums, and annotation types use PascalCase.
- Methods and variables use camelCase.
- Constants use UPPER_SNAKE_CASE.
- Packages use lowercase.
- Boolean names communicate a clear predicate.
- Exception names communicate the represented failure.
- Abbreviations are avoided unless canonical or widely established.

Canonical terminology in GLOSSARY.md takes precedence over casual Java synonyms. Database Transaction, Payment Transaction, Payment Authorization, Code Repository, Spring Repository, Product Variant, and Stock Reservation MUST remain qualified where ambiguity would otherwise result.

## 35. Packages

Package structure MUST reflect the Modules, Domain ownership, and dependency direction established by ARCHITECTURE.md. Package visibility SHOULD reinforce those boundaries.

Arbitrary package-by-layer structures MUST NOT collapse Module ownership or enable cross-Module access to internal Entities, Repositories, or implementation details. Generic packages such as common, shared, misc, model, or util require a narrow, governed purpose and MUST NOT become dumping grounds.

This document does not invent an exact root package name.

## 36. Visibility

Code MUST use the narrowest practical visibility. private and package-private SHOULD be preferred when broader exposure is unnecessary.

Public classes and methods create compatibility, ownership, documentation, and testing obligations. Production visibility MUST NOT be widened solely to simplify a test; tests SHOULD exercise public behavior or use a justified package boundary.

## 37. Methods

Methods SHOULD be focused, cohesive, and explicit about inputs, outputs, side effects, and failure behavior.

Excessive parameter lists, boolean flags that select unrelated behavior, hidden side effects, and methods combining validation, persistence, provider calls, mapping, and Domain decisions SHOULD be decomposed along real responsibilities.

Method extraction and abstractions MUST clarify genuine behavior rather than fragment straightforward code.

## 38. Constructors and Factories

Constructors MUST establish valid required state where applicable and MUST NOT publish a partially initialized object.

Named factories MAY clarify creation variants, preserve invariants, return a subtype, or hide justified construction complexity. A Factory MUST NOT bypass the owning Aggregate or Value Object invariants.

Factories SHOULD NOT conceal simple construction or introduce abstraction without a meaningful semantic benefit.

## 39. Builders

Builders MAY support complex immutable construction or readable test setup. They SHOULD NOT be introduced for trivial objects.

A production builder MUST enforce or delegate all required invariants before producing a Domain object. It MUST NOT make invalid Aggregate or Entity state publicly constructible.

Test builders MUST make intentional invalid-state creation explicit when a negative test requires it.

## 40. Domain Objects

Java Domain code MUST preserve Aggregate boundaries, Entity identity, Value Object semantics, invariants, and canonical lifecycle terminology.

Mutation MUST be owned and protected by behavior that preserves invariants. Public setters and anemic mutation SHOULD be avoided where behavior belongs to the Domain. Business behavior MUST NOT be forced into an Entity when an approved Domain Service owns cross-concept behavior or an Application Service owns orchestration, Authorization, Database Transactions, or external effects.

Java code MUST keep a Database Transaction distinct from a Payment Transaction. SPRING.md owns the Spring implementation mechanism for Database Transaction boundaries.

## 41. Payment Safety

Java types and methods MUST preserve the distinctions among Payment, Payment Attempt, Payment Provider, Payment Redirect, Payment Authorization, Capture, Void, Payment Transaction, Refund, Refund Transaction, Chargeback, Settlement, and Idempotency Key.

Provider-dependent authoritative Payment state MUST require validated Payment Provider evidence. A Payment Redirect, browser result, client-provided success flag, or unvalidated Callback or Webhook MUST NOT establish Payment success.

Retries and duplicate processing MUST preserve idempotency, reconciliation, and prevention of duplicate financial or Order effects. A boolean such as paymentSuccessful MUST NOT become authoritative merely because an untrusted client or redirect supplied it.

Authoritative financial calculations MUST follow sections 22 and 23.

## 42. Inventory Safety

Java implementation MUST preserve Inventory ownership of authoritative Stock, Stock Reservation, Available-to-Sell, Stock Adjustment, and Stock Movement state.

Stock Reservation creation, expiry, release, and finalization MUST preserve invariants under concurrency, rollback, duplicate requests, and retries. Java code MUST prevent overselling and MUST NOT use mutable shared in-memory state as authoritative Inventory state.

Client, Product Catalogue, search, reporting, and other projection state MUST NOT become authoritative Stock or Available-to-Sell truth.

## 43. Authorization

Java code MUST enforce Authorization through trusted server-side policy at applicable entry, Use Case, object, property, and Domain-state boundaries.

Authorization MUST NOT be inferred from UI state, hidden controls, client flags, a client-provided Role or Permission, or object identifiers alone. The Principal's authority over the exact Resource and action MUST be verified.

Identity, Principal, Role, Permission, Claims, Scope, Session, Access Token, and Refresh Token semantics remain governed by GLOSSARY.md, SECURITY-STANDARDS.md, PRODUCT.md, and approved Identity Contracts.

## 44. Sensitive Data

Java object design MUST minimize collection, retention, copying, and exposure of Sensitive Data. Long-lived objects SHOULD NOT contain Secrets, credentials, tokens, or other sensitive values when a narrower lifetime is possible.

Sensitive Data MUST NOT appear in Logs, toString(), exception messages, assertion messages, committed test fixtures, generated equality diagnostics, or telemetry attributes. Redaction MUST occur before an unsafe boundary, not after emission.

## 45. Serialization Boundaries

Arbitrary Domain objects MUST NOT be made serializable for framework convenience. Serialization belongs to an explicit Contract and Adapter boundary with project-owned models and governed fields.

Java native serialization MUST NOT be introduced as an external Contract unless specifically governed. Serializable MUST NOT be applied as a default marker.

Deserialization of untrusted input MUST use explicit safe types and applicable validation. Dynamic or polymorphic deserialization requires a bounded, reviewed allowlist.

## 46. Concurrency

Services SHOULD be stateless or explicitly thread-safe. Shared mutable state requires clear ownership, synchronization, visibility, atomicity, resource bounds, and focused tests.

Code MUST NOT assume ordinary collections are thread-safe, Spring singleton Beans make mutable state safe, or volatile makes compound operations atomic.

Concurrency that affects Payment, Inventory, Order, Identity, or Authorization correctness requires invariant, race, retry, and failure verification proportionate to Risk.

## 47. Virtual Threads

Java 21 virtual threads are not selected as the repository concurrency model by this document. They MUST NOT be adopted silently.

Any adoption requires evidence for Spring and dependency compatibility, blocking workload characteristics, Database connection limits, provider limits, thread-local and security-context behavior, observability, testing, performance, and deployment behavior.

Until governed otherwise, virtual threads remain an implementation option requiring applicable Architecture and Decision review, not a baseline requirement.

## 48. Resource Management

Owned AutoCloseable resources MUST use try-with-resources where practical. Streams, files, sockets, and other integration resources MUST close according to explicit ownership.

Code MUST NOT manually close framework-managed or shared resources it does not own. Cleanup failures and partial processing MUST be handled according to the applicable Contract and recovery behavior.

## 49. Input and Output

Code MUST NOT load unbounded files, request bodies, archives, provider payloads, or result sets fully into memory. Bounded or streaming approaches SHOULD be used when payload size can be material.

Untrusted content MUST be validated according to SECURITY-STANDARDS.md and the applicable Contract. Paths, filenames, encodings, content types, archive expansion, and resource limits MUST be handled safely where applicable.

## 50. Randomness

Security-sensitive tokens, reset codes, nonces, unpredictable identifiers, and cryptographic values MUST use an approved cryptographically secure random facility.

java.util.Random and other predictable generators MUST NOT be used for security-sensitive values. This document MUST NOT invent token formats or generation schemes owned by Identity, security, or an external Contract.

Non-security test randomness MUST be deterministic and reproducible when a failure must be diagnosable.

## 51. Cryptography

Custom cryptographic algorithms or protocols are prohibited. Java code MUST use approved platform or library mechanisms governed by SECURITY-STANDARDS.md.

Cryptographic keys, algorithms, modes, and protocol parameters MUST NOT be hard-coded where security policy owns selection or rotation. Certificate, hostname, signature, and integrity validation MUST NOT be bypassed.

## 52. Logging

Java application logging MUST use the repository-established SLF4J abstraction. This document does not select a logging backend.

System.out and System.err MUST NOT be used for application logging. Parameterized logging SHOULD be used where supported, and expensive diagnostic values SHOULD NOT be computed when the relevant level is disabled.

Logs MUST preserve applicable Correlation ID and structured context while complying with Sensitive Data and Audit Record rules. Diagnostic Logs MUST NOT be treated as Audit Records.

## 53. Assertions

Java assert MUST NOT enforce production Domain, security, Payment, Inventory, Authorization, or input-validation invariants because assertions may be disabled.

Production invariants MUST use explicit validation and failure behavior. Test assertions MUST remain clear, deterministic, and free of Secrets or unnecessary Sensitive Data.

## 54. Reflection

Reflection SHOULD be avoided where ordinary type-safe Java is sufficient. Framework-required reflection is acceptable within the approved framework boundary.

Custom reflective mechanisms require justification, bounded access, tests, security review where applicable, and consideration of runtime, performance, deployment, and compatibility behavior.

Reflection MUST NOT bypass Module, visibility, serialization, validation, or security boundaries.

## 55. Annotation Use

Annotations SHOULD express real language, framework, validation, or tooling semantics. They MUST NOT hide substantial business behavior, side effects, Authorization, or control flow without strong justification and reviewable implementation.

Custom annotation frameworks require dependency, Architecture, testability, and maintenance justification. Spring annotations remain governed by SPRING.md and MUST NOT leak into Domain code contrary to that standard.

## 56. Lombok and Code Generation

This document does not select Lombok or another Java code-generation library. Adoption requires repository dependency governance and compatibility evidence.

If later adopted, generated code MUST NOT hide Domain invariants, produce unsafe Entity equality, expose Sensitive Data through generated toString(), or obscure constructors and ownership required for correctness.

Generated source MUST remain reproducible, reviewable through its source or generator, and subject to the same security and testing requirements as human-authored code.

## 57. Mapping

Mapping among API DTOs, application commands and results, Domain objects, persistence representations, and provider Contracts MUST remain explicit enough to preserve ownership, writable fields, validation, security, and semantic distinctions.

This document does not select MapStruct or another mapper library. Reflection-heavy or generated mapping MUST NOT conceal mass assignment, Sensitive Data exposure, provider leakage, or Domain invariant bypass.

## 58. Comments and Javadoc

Comments and Javadoc SHOULD explain rationale, constraints, invariants, security-sensitive behavior, lifecycle semantics, and non-obvious public Contracts. They MUST remain accurate and MUST NOT narrate obvious syntax.

Public reusable APIs and difficult Domain rules SHOULD receive useful documentation where warranted. Documentation remains governed by DOCUMENTATION-STANDARDS.md.

## 59. Testing

Java-specific tests MUST comply with TESTING-STANDARDS.md. They SHOULD cover deterministic behavior, boundary values, exception behavior, equality and Value Object semantics, Money, time, collections, concurrency where relevant, and security-sensitive utilities.

Payment tests MUST verify provider-evidence authority, idempotency, reconciliation, and duplicate-effect prevention. Inventory tests MUST verify Stock Reservation and Available-to-Sell correctness under concurrency. Authorization tests MUST include denial and object-level paths.

This standard does not introduce arbitrary coverage percentages. SPRING.md owns Spring-specific test-context and framework-integration guidance.

## 60. Test Data

Test fixtures MUST be deterministic, minimal, isolated, and free of production Secrets or Sensitive Data.

Test factories and builders MUST NOT conceal invalid Domain state unless the test intentionally exercises invalid input. Generated test data SHOULD support reproducible failures through fixed inputs or recorded seeds.

## 61. Performance

Material optimizations MUST be supported by measurement, profiling, a Requirement, an SLO, or capacity evidence. Code SHOULD avoid obvious algorithmic waste, unbounded collections, unnecessary allocation on evidenced hot paths, repeated work, and accidental N+1-style processing visible at the Java or application layer.

Readability, correctness, and security MUST NOT be traded for speculative micro-optimization. Persistence-specific query optimization remains outside this document.

## 62. Dependency Boundaries

Third-party libraries MUST have a justified capability and follow repository dependency, license, maintenance, version, and security governance.

Provider SDK and infrastructure types MUST remain behind appropriate Ports and Adapters and MUST NOT spread through Domain APIs. A dependency SHOULD NOT be added merely to replace a small amount of clear, safe standard-library code.

This document does not select a build tool, ORM, mapper, logging backend, HTTP client, resilience library, or JDK distribution.

## 63. Deprecated, Incubator, and Preview Features

Deprecated APIs MUST NOT be introduced in new code without documented justification, compatibility assessment, and a removal plan.

Java preview or incubator features MUST NOT be used in production baseline code unless explicitly approved through applicable Architecture and Decision governance, build and runtime support, deployment compatibility, and focused testing.

Preview or incubator use MUST NOT become an accidental repository baseline through a local compiler flag.

## 64. Prohibited Practices

The following are prohibited:

- float or double for authoritative Money calculations;
- mutable global or static state;
- field injection as a Java or Spring practice;
- production invariants enforced with Java assert;
- swallowed exceptions or empty catch blocks;
- broad uncontrolled exception catches;
- System.out or System.err application logging;
- raw generic types;
- unsafe unchecked casts;
- Secrets or Sensitive Data in source, Logs, exceptions, assertions, or committed fixtures;
- Domain-wide framework or provider leakage;
- Java native serialization as an accidental external Contract;
- casual parallelStream() use;
- ungoverned preview or incubator features;
- client state treated as Authorization, Payment, Inventory, Price, Role, Permission, or provider truth; and
- language convenience used to bypass an Aggregate invariant, Module boundary, or governing Requirement.

## 65. Deviations and Exception Governance

This document does not create a Java Exception type or independent waiver process. A deviation MUST document the affected rule, rationale, Risk, scope, owner, and expiry or remediation when temporary.

The applicable Coding Exception, Security Exception, Testing Exception, Documentation Exception, Decision Record, ADR, or other governing process MUST be used according to the concern being changed.

A deviation from this standard MUST NOT waive a core Requirement or an applicable SPRING.md requirement. Every applicable formal Exception remains required, and a mandatory security Requirement may be waived only through an approved Security Exception.
